# 面评家：AIC 参赛项目改进评审

评审日期：2026-09-05。代码基线：`1c203cc`。参赛方向由项目作者确认：AIC 全球校园人工智能算法精英赛 / 算法创新赛 / 赛题 2：AI+软件创新。

本次交付为根目录 `AGENTS.md` 和本评审，不包含业务代码修复。结论基于当前源码、现有离线测试、前端构建及合成数据复现；真实千问效果、浏览器实机交互和 Docker 镜像运行未在本次验收。

## 1. 总体判断与赛道对齐

项目具备完整的产品主线：选岗、解析简历、匹配分析、多轮面试、个人报告。匿名访问令牌、岗位审核、状态机约束、事务和重试保护已经落地，适合继续打磨为这个赛道的参赛作品。

当前最影响竞争力的是三个缺口：关键页面存在可复现的交互问题；简历信息还没有进入面试追问上下文；评分与创新效果缺少可核验的实验支撑。建议围绕“针对个人经历追问，并提供能定位原话的改进反馈”形成一条技术与产品相互支撑的主线。

本次参考组委会 2026-05-06 发布的 [AI+软件创新规则](https://www.aicomp.cn/tracks/tracks-2/3792.html)，于 2026-09-05 核对。官方评分及本项目的应对建议如下：

| 评分项 | 分值 | 本项目应重点提供的证据（评审建议） |
| --- | ---: | --- |
| 创新性 | 20 | 个性化追问策略、证据约束及与基线的对照结果 |
| 技术实现 | 20 | 异常恢复、评分可靠性、耗时与成本记录 |
| 功能完整性 | 20 | 从上传到报告的连续演示及失败后恢复 |
| 方案完整性 | 20 | 架构、核心算法说明、测试报告、部署说明 |
| 应用价值 | 15 | 目标用户试用和练习前后变化 |
| 总结与展望 | 5 | 已验证成果、局限与分阶段迭代计划 |

规则要求软件说明、功能视频、核心算法说明、测试报告，并提供便于验证的软件形态。下文优先级是本次评审建议，不是官方评分预测；具体赛区截止时间尚未确认。

## 2. 先修复的可复现问题

### 2.1 报告重试成功后，页面仍显示错误

- 位置：[ReportView.vue](../frontend/src/admin/ReportView.vue)，第 8–15、140–146 行。
- 触发：首次获取报告失败，点击“立即生成评估报告”，第二次请求成功。
- 原因：`runEvaluate()` 写入 `state.report` 后没有清空 `state.error`，模板优先显示错误分支，报告和图表都不会挂载。
- 组件渲染复现：`report_loaded=true`、`error_still_visible=true`、`chart_nodes=0`。
- 建议：成功时清空错误，等待报告分支挂载后绘图；明确区分无访问凭证、未结束、生成中和生成失败。
- 验收：首次失败 → 重试成功，不刷新页面即可看到总分、维度和雷达图。

### 2.2 匹配分析成功后，雷达图没有初始化

- 位置：[ResumeAnalysisView.vue](../frontend/src/views/ResumeAnalysisView.vue)，第 60–73、214–230 行。
- 触发：上传成功并完成匹配分析。
- 原因：`loadMatch()` 在 `matchLoading=true` 时调用 `renderChart()`。此时仍显示加载分支，`chartEl` 尚未挂载；`finally` 才结束加载，之后没有再次绘图。
- 组件渲染复现：`match_loaded=true`、`chart_nodes=1`、`chart_initializations=0`。
- 建议：结束加载并等待 DOM 更新后初始化图表；重新上传时销毁旧实例或正确绑定新容器。
- 验收：首次上传、匹配重试、换简历三种路径都能显示当前数据的雷达图。

### 2.3 证据被全部过滤后，报告仍能得到满分

- 位置：[evaluator.py](../backend/app/agents/evaluator.py)，第 127–160 行。
- 已有保护：服务端会删除无法在候选人原话中找到的证据，并重新计算加权总分。
- 剩余问题：过滤证据不会改变对应评分的有效性，分数仍参与总分。模型漏掉某一维度时，又直接把该维度补为 0 分。
- 合成输入复现：两个维度都返回 10 分和虚构证据，过滤后证据数为 `[0, 0]`，总分仍为 `100`；两个等权维度仅一个有 8 分时，另一个自动补 0，总分为 `40`。
- 影响：用户无法区分“表现较差”“没有被考察”和“模型结果不可信”，会削弱项目的证据化评估主张。
- 建议：增加维度状态、证据覆盖率和证据定位；对无可靠依据的评分标为“证据不足/待补充”，限制生成确定性总评。总分是否按有效维度重归一化，应与覆盖率一起明确展示，避免只考一个维度也呈现完整能力分。
- 验收：虚构证据、漏维度、未考察维度、跨维度误引均有独立用例；显示的结论能够追溯到消息与评分规则。

### 2.4 模型返回合法 JSON，但字段类型不对时仍可能中断流程

- 位置：[candidates.py](../backend/app/api/candidates.py)，第 106–125 行；[graph.py](../backend/app/agents/interviewer/graph.py)，第 198–212 行；[llm.py](../backend/app/llm.py)，JSON 提取与返回部分。
- API 复现：模拟简历解析返回 `{"basic": null}`，上传接口返回 HTTP 500，触发点为 `parsed.get("basic", {}).get("name")`。临时上传文件仍被正确清理。
- 协议复现：模拟 `next_question` 为数组，图执行后在转换 `InterviewTurn` 时抛出 `ValidationError`，没有进入问题兜底。
- 建议：为简历、面试决策、匹配和报告分别建立结构化输出模型，在读取字段前验证类型；协议错误纳入受控重试或降级，返回可理解的状态。
- 验收：覆盖 `null`、错误嵌套类型、空对象、非有限分数和非法 action，主流程不出现未处理的 500。

### 2.5 配置中的题目上限没有传入新面试状态

- 位置：[config.py](../backend/app/config.py)，第 50–51 行；[interviews.py](../backend/app/api/interviews.py)，第 54–64 行。
- 复现：进程内把 `settings.max_total_q` 改为 `2`，新状态仍是默认的 `15`。
- 原因：`_load_state()` 调用 `initial_state()` 时没有传入配置值。
- 建议：创建会话时冻结有效规则到状态快照；已有面试继续沿用其创建时的规则，避免中途改配置改变面试条件。
- 验收：新面试使用配置上限，已有快照保持原上限；提示词与前端展示的规则一致。

## 3. 最值得加强的核心能力

### 3.1 把简历与匹配缺口接入追问

当前匹配 Agent 会读简历，但面试状态初始化仅传岗位维度、岗位名和风格；[面试提示词](../backend/app/agents/interviewer/prompts.py)只读取大纲、历史对话和最新回答。合成简历中的专用项目标记没有出现在实际构造的面试提示词里。

这意味着面试官能沿着用户已经说出的内容追问，却不能主动根据上传简历核验某个项目成果；“压力面核验简历亮点”的界面描述还缺少这一层输入支持。

建议实现一条可解释的策略：

1. 从简历提取项目事实、个人贡献和待核验声明，保留原文位置。
2. 将这些事实映射到岗位维度，结合面试前匹配缺口形成考察计划。
3. 在固定轮次预算内，优先追问尚未覆盖或证据不足的维度，避免重复追问。
4. 每轮记录目标维度、缺少的信息、采取的动作和简短理由，报告能回看这条记录。

验收案例可以固定为同一个后端岗位、两份不同项目经历的简历，展示问题如何分别围绕数据库优化和异步任务设计展开。该能力需要实际实现与实验后再写成创新成果。

### 3.2 把“原话存在”推进到“评分有依据”

当前报告证据校验是全场候选人文本中的子串匹配，未保留消息 ID 或维度关联。[评估调用](../backend/app/api/interviews.py)传给评估器的消息也只有角色和正文；数据库已有的 `dimension`、消息 ID 未一并使用。评估输入还将每条消息截断到前 500 字，长回答后半段的关键事实可能不可见。

建议建立统一的维度评分规则，给出分档描述；证据包含消息 ID、原话区间和对应评分点。长回答优先按评分相关信息抽取片段并保留原文索引。报告可点击证据返回对应问答，明确展示已考察范围和仍需补充的内容。

三种风格目前共享协议，但人格描述与决策处于同一次模型调用中，措辞规则也可能改变追问数量与覆盖范围。若要宣称评估公平，应通过同一素材的风格对照验证，或将提问决策与语言风格改写分开。

### 3.3 让等待、失败和离线演示都有完整路径

[前端请求](../frontend/src/api/index.js)在 90 秒中止；[模型配置](../backend/app/config.py)默认单次超时 60 秒，[chat_json](../backend/app/llm.py)最多尝试三次，名义等待预算可达约 180 秒。收尾请求在提交会话后还同步执行报告评估，因此存在前端已超时、后端仍在执行的窗口；这属于配置与流程推导，本次未做真实延迟实测。

同时，面试结束语和完成卡片无条件宣称“报告已生成”，但评估失败会被后端捕获并留下空报告。现有报告缓存可避免已完成结果的重复生成，但还没有独立的生成中状态来协调并发重试。

建议先补充清晰的任务状态、失败原因和恢复入口，再根据实测耗时决定是否将长任务独立执行。上传、匹配和报告使用幂等标识或内容版本缓存，控制重复调用；报告生成需要单次任务认领。日志增加关联 ID、模型版本、阶段、耗时和 token，避免记录隐私正文。

演示脚本目前称断网可展示简历上传，但新上传会调用真实解析模型，匹配也依赖模型，无法沿新上传路径完成全流程。[make_demo.py](../scripts/make_demo.py)提供的是预置记录，不是完整离线模型模式。

建议准备明确标注的离线演示模式，使用合成简历与固定回放数据，并与实时模式区分。两种模式都能从入口走到报告，离线数据不作为真实模型效果或成本证据。

## 4. 用实验支撑创新性和应用价值

README 中“追问触发率 ≥60%”“重复评分极差 ≤1”“单场成本 <¥1”目前是目标。仓库有离线功能测试和调用用量日志，未发现可复现的效果评测脚本、按场汇总的成本记录或这些目标的实测结果。

建议先聚焦 1–2 类应届技术岗，用合成数据或经同意并去标识的样本建立小规模固定评测集。可先准备 30–50 组问答，由两位具备相关岗位知识的评审标注回答是否充分、缺少什么信息及合理评分区间。此规模是起步建议，不足以支持普遍公平性结论。

| 要证明的能力 | 建议指标与验证方式 |
| --- | --- |
| 追问有效 | 对“需要补充/已经充分”的答案分别统计正确追问与无效追问；不能仅追求触发比例越高越好 |
| 简历个性化 | 同岗不同简历对照，检查问题是否准确引用该候选人的真实项目，并与无简历输入版本比较 |
| 流程可靠 | 正常、短答、跑题、恶意指令、模型超时、错误 JSON、重复请求等条件下的完成率与规则违规率 |
| 证据可靠 | 引用可定位比例、与目标维度的相关性，以及无证据评分的拦截情况 |
| 评分合理 | 与人工评分的平均绝对偏差、重复评估的波动、未考察维度的处理结果 |
| 等待与成本可控 | 按解析、匹配、逐轮追问、评估分别记录耗时及 token，汇总整场 p50/p95、错误率和费用 |
| 帮助用户改进 | 同意参与的目标用户完成练习前后两次等难度任务，记录完成率、反馈可执行性和评分变化，说明样本局限 |

对照至少包含“固定题目或基础提示词版本”和“当前/改进版本”；在同一模型、同一数据和相近调用预算下比较。保存数据版本、模型名称、提示词版本、实验条件及原始结果。

特别注意：[评估接口](../backend/app/api/interviews.py)第 442–450 行会直接返回已有报告。重复请求该接口三次只验证缓存稳定，不能证明模型评分一致。真实一致性实验需要对固定输入独立执行评估，并记录每次结果和成本；本次未开启这些付费调用。

## 5. 补齐可以交给评委的材料

仓库内已看到 README、演示脚本、更新清单和 CI。未在仓库中发现独立的完整技术方案、真实模型实验报告和演示视频；这些材料也可能存在于仓库外。

建议形成以下交付包：

- **产品与技术方案**：明确求职者痛点，给出架构图、状态转换、输入输出、核心追问策略、评分规则和团队贡献。
- **测试报告**：离线功能验证与真实模型实验分别记录，附失败案例、修复前后证据和指标原始数据。
- **可复现部署**：补上前端部署与 API 代理。当前 Compose 仅有后端，不能单凭该文件启动整站；完整镜像构建、持久化和页面刷新访问均需实际走查。
- **演示视频与脚本**：突出“简历事实 → 针对性追问 → 原话证据 → 改进建议”的连续过程，展示一次失败恢复，说明哪些数据是预置演示。
- **用户与复用证据**：保留真实试用反馈、样本说明和开源依赖出处；后续公开试用补充数据保存、删除、访问凭证恢复及调用配额设计。

现有脚本对同类产品使用了“一次性问答/题库刷题”等概括，本次没有验证这些竞品结论，建议在实际调研前收敛措辞。数字人形象、Agent 数量和所用框架可以解释实现，但技术贡献应落在明确策略及其可测增益上。

## 6. 推荐实施顺序

1. **核心流程可用**：修复两处页面问题，补充报告状态和结构化字段校验，把配置上限接入；增加覆盖这些真实故障的针对性测试。
2. **形成主打能力**：接入简历与岗位缺口，完善证据定位、未考察维度处理和追问策略，建立固定案例。
3. **产出实验结果**：完成基线对照、评分核验、耗时成本统计与小规模用户试用；根据结果调整策略。
4. **完成参赛交付**：技术方案、测试报告、完整部署、实时/离线演示及视频与实际能力一致。

语音输入、历史练习对比、报告导出等可在主线稳定后补充，其中历史练习对比更直接服务于“练习后是否进步”的产品价值。实施排期需要结合尚未确认的比赛截止时间和团队人力。
